**Risk**: Medium. FCPXML is documented but different Resolve versions may have variations.

**What was done**: 
- Generated FCPXML follows Apple's FCPXML specification v1.9
- Created proper clip elements with source in/out points
- References original media file via absolute path

**What needs verification**:

- Verify cuts are applied correctly
- Verify video/audio sync is maintained

### 2. FCPXML Behavior

**Assumption**: FCPXML with multiple clips from the same source file, each with different in/out points, will create a timeline with gaps where cuts are removed.

**Risk**: Medium. This is the intended behavior but needs verification.

**What was done**:
- Each keep interval becomes a separate clip in the FCPXML
- Clips reference the same source media with different tcIn/tcOut values

**What needs verification**:
- Import FCPXML and check that cuts create gaps (not black frames)
- Verify that audio and video stay in sync

### 3. Whisper Behavior

**Assumption**: `mlx-whisper` on Apple Silicon will produce word-level timestamps with reasonable accuracy.

**Risk**: Medium. MLX Whisper is actively developed and APIs may change.

**What was done**:
- Implemented transcription with `mlx_whisper.transcribe()`
- Requested word-level timestamps via `return_word_timestamps=True`
- Fallback to CPU-based `whisper` package

**What needs verification**:
- Test with actual audio file
- Verify word timestamps are accurate
- Check that whisper model downloads correctly
- Test different model sizes (tiny, base, small)

### 4. UHM Model Behavior

**Assumption**: UHM ONNX model produces predictions every 20ms with the expected output format.

**Risk**: High. The actual model output format has NOT been verified.

**What was done**:
- Implemented chunking with 30-second windows and 20ms stride
- Predictions are processed as (num_windows, num_classes)
- Classes: ["not filler", "uh", "um", "hmm", "and", "other"]

**What needs verification**:

### 5. Frame Rate Assumptions

**Assumption**: Common frame rates can be accurately represented as fractions.

**What was done**:

- Handles 23.976 (24000/1001), 24, 25, 29.97 (30000/1001), etc.
- Falls back to approximate fraction for other rates

**What needs verification**:
- Test with actual videos at various frame rates
- Verify FCPXML imports correctly with different frame rates

### 6. Audio Format Assumptions

**Assumption**: All input audio can be converted to 16kHz mono for UHM processing.

**What was done**:

- Resampling implemented via scipy.signal.resample

## Architecture Decisions

### 1. Modular Design

**Decision**: Split functionality into separate modules (media, uhm, transcription, intervals, captions, timeline, gui).

**Rationale**: 
- Clear separation of concerns
- Easier testing of individual components
- Better maintainability

**Files**:
- `models.py`: Data structures (Interval, FillerDetection, Word, Caption, MediaInfo, AnalysisResult)
- `intervals.py`: All interval mathematics
- `media.py`: FFmpeg/FFprobe integration
- `uhm.py`: UHM model integration
- `transcription.py`: Whisper integration
- `captions.py`: Caption generation and remapping
- `timeline.py`: FCPXML generation
- `app.py`: Main pipeline orchestration
- `gui.py`: Tkinter GUI

### 2. Timestamp Representation

**Decision**: Use float seconds for all timestamps internally.

**Rationale**:
- Simple and intuitive
- Avoids frame-based complexity
- Easy to convert to/from frames when needed
- Python's float has sufficient precision for sub-frame accuracy

**Trade-off**: Floating-point drift could accumulate over very long timelines, but this is acceptable for the MVP.

### 3. Interval Representation

**Decision**: Use half-open intervals [start, end) - inclusive of start, exclusive of end.

**Rationale**:
- Consistent with Python conventions
- Avoids ambiguity at boundaries
- Makes merging and adjacency detection clearer

### 4. FCPXML Generation

**Decision**: Generate FCPXML with multiple clips from the same source, each representing a keep interval.

**Rationale**:
- References original media without re-encoding
- Each clip has different in/out points
- Creates gaps in the timeline where cuts are removed

**Trade-off**: Different approach might be needed if Resolve doesn't handle this well.

### 5. Model Caching

**Decision**: Download models on first use and cache in Hugging Face Hub cache directory.

**Rationale**:
- Standard practice for ML applications
- Avoids committing large model files to repository
- Respects upstream licensing (users must accept model licenses)

### 6. Caption Generation Strategy

**Decision**: Generate captions from word timestamps, grouping words into phrase-level segments.

**Rationale**:
- Word-level timestamps from Whisper enable accurate captions
- Phrase-level is more readable than word-level
- Configurable length limits for readability

**Trade-off**: May need adjustment based on actual Whisper output quality.

### 7. GUI Framework

**Decision**: Use Tkinter for the GUI.

**Rationale**:
- Included with Python (no additional dependencies)
- Works well on macOS
- Simple to implement
- Sufficient for MVP requirements

**Trade-off**: Not as polished as other frameworks, but adequate for MVP.

### Setup (Fresh Start)

```bash

git clone <repository>
cd resolve-autocut

# Create environment with uv
uv venv --python 3.12.13
source .venv/bin/activate
```

### Run Tests

```bash
# All tests
python -m pytest tests/ -v

python -m pytest tests/ --cov=src/resolve_autocut --cov-report=html

```

### Run GUI

```bash
python -m resolve_autocut.gui
```

### Run Pipeline Programmatically

```python
from resolve_autocut import ResolveAutoCut, run_analysis_pipeline

# Using the app class
app = ResolveAutoCut(
    cut_padding=0.05,
    whisper_model="base",
    confidence_threshold=0.5
)

analysis = app.analyze("/path/to/video.mp4")
app.export_all(analysis, "/path/to/output", base_name="my_video")

# Or using the convenience function
result = run_analysis_pipeline(
    media_path="/path/to/video.mp4",
    output_dir="/path/to/output",
    cut_padding=0.05
)
```

### Test with Sample Video

